# VIPER 0.1.0a3 Core Release Contract

## Release requirements

The release contains VIPER's experiment execution, verification, storage,
restoration, catalog, knowledge, and MCP interfaces. Experimental source-analysis
and contract-planning subsystems are excluded.

The [public authoring contract](v0.1.0a3-public-authoring-contract.md) and
[execution-policy contract](execution-policy-contract.md) define the required
API and runtime behavior. The [release report](../releases/0.1.0a3.md) records
candidate identities and validation results.

| ID | Implementation obligation |
|---|---|
| `CRB-01` | Preserve the complete pre-cleanup repository state at `codex/archive-v0.1.0a3-pre-cleanup`. |
| `CRB-02` | Remove the System Impact, CodeQL, graph-localization, contract-plan, scheduling, research-memory, fixture, and workday-journal surfaces listed in this contract. |
| `CRB-03` | Remove their API, CLI, MCP, documentation, packaging, and test references while preserving similarly named scientific knowledge records. |
| `CRB-04` | Retain and verify core execution, verification, storage, restoration, catalog, knowledge, and MCP behavior added after `v0.1.0a2`. |
| `CRB-05` | Build wheel and source distributions whose inventories exclude every removed experimental path and symbol. |
| `CRB-06` | Install the candidate outside the checkout and pass the public API, CLI, generated-project, CPU quickstart, and supported-Python gates. |
| `CRB-07` | Run the candidate wheel through the applicable Mantra GPU acceptance path before PyPI publication. |
| `CRB-08` | After the public authoring contract closes and the refreshed candidate passes every release gate, publish those exact artifacts through the signed-tag workflow and record their identities. |

## Excluded content

The wheel and source distribution must exclude these removed subsystem owners:

- `src/viper/system_impact/`, `src/viper/_system_impact/`,
  `src/viper/scheduling.py`, and `src/viper/_contract_traceability.py`.
- `tools/codeql/`, `tools/plan/`, `tools/refresh_contract_baselines.py`, and `plans/`.
- `tests/data/system_impact/`, `tests/test_codeql_analysis.py`,
  `tests/test_codeql_graph_semantics.py`, `tests/test_contract_documentation.py`,
  `tests/test_contract_target_parity.py`, `tests/test_contract_traceability.py`,
  `tests/test_plan_check.py`, `tests/test_system_impact.py`, and
  `tests/test_system_impact_explain.py`.
- Development contracts, local editor settings, and workday journals.

Public operation inventories must exclude `analyze_impact` and `explain_impact`.
Scientific knowledge operations such as `search_impacts`, `publish_impact`, and
`publish_impact_policy` remain public. `plan_diff` continues to compare run plans.

[MANIFEST.in](../../MANIFEST.in) controls source-distribution inclusion.
[Distribution tests](../../tests/test_distribution_contents.py) inspect the built archives.
The preservation branch `codex/archive-v0.1.0a3-pre-cleanup` retains the removed
experimental work; recreating it is unnecessary.

## Candidate validation

1. Run the repository checks against the candidate source:

   ```bash
   source .venv/bin/activate
   make check
   make check-integration
   make check-release
   python -m build
   python -m twine check dist/*
   ```

2. Inspect the wheel and source-distribution inventories. Check retained modules,
   excluded paths, package version, Python support, dependencies, and metadata.
3. Install the candidate outside the checkout. Run public import, CLI, generated
   workspace, and CPU quickstart checks using the installed distribution.
4. Pass [CI](../../.github/workflows/ci.yml) on every advertised Python version
   for the candidate commit.
5. Install that exact wheel on the designated Mantra GPU host and run numerical
   acceptance and checkpoint profiling. Run the execution-policy contract's
   [real-device checks](execution-policy-contract.md#10-tests-and-remaining-acceptance).
6. Record the candidate commit, filenames, byte counts, SHA-256 digests, test
   outputs, CI run, GPU identity, and checkpoint profile in the release report.
7. After explicit user approval, use the [release workflow](../../.github/workflows/release.yml)
   to publish through TestPyPI and PyPI. Verify clean installation and registry
   hashes against the validated distributions.

A rebuilt distribution requires validation of its new identity. The existing
[Mantra receipt](receipts/v0.1.0a3-mantra-gpu.json) identifies its tested wheel
by SHA-256; use it only for that wheel.

## Verification rules

| Rule | Executable condition |
|---|---|
| `release.archive.preserved` | The remote preservation branch resolves to the exact pre-cleanup commit. |
| `release.experimental.absent` | Both built archives omit the [excluded content](#excluded-content). |
| `release.public.surface` | Installed-wheel API, CLI, and MCP inventories omit `analyze_impact` and `explain_impact` and retain all approved knowledge operations. |
| `release.knowledge.exact` | The existing ontology, vector, immutable-publication, exact-filter, similarity, API, CLI, and MCP tests pass while Python reports `usearch` as absent. |
| `release.local.accepted` | `make check`, `make check-integration`, `make check-release`, the CPU quickstart, and clean-install checks pass for the candidate. |
| `release.python.compatible` | CI passes under every Python version declared in `pyproject.toml`. |
| `release.mantra.accepted` | Mantra installs the candidate wheel by path or digest and completes the agreed GPU acceptance execution. |
| `release.identity.equal` | Local, CI, TestPyPI, and PyPI filenames and SHA-256 digests identify the same wheel and source distribution. |

## Acceptance

The candidate must run the CPU quickstart and generated workspace after a clean
installation. Knowledge publication, exact filtering, cosine similarity, and
Python/CLI/MCP queries must retain their tested behavior. The same wheel must
pass the designated GPU acceptance path.

An archive containing a removed module, an installed public operation from the
removed subsystem, a failed supported-Python check, or a mismatch between
validated and published hashes rejects the candidate.

## Deferred work

Knowledge similarity remains exhaustive cosine-distance search after exact
filters. Any later acceleration must establish latency, memory, distance parity,
stable ties, and installation coverage on representative workloads. Approximate
search requires measured recall and persisted-index consistency.
