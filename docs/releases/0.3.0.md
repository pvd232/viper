# VIPER 0.3.0

VIPER now publishes completed experiment files in the background and manages
local copies through one artifact resolver. Artifact references and saved run
records keep their existing identities.

```bash
python -m pip install --upgrade 'viper-provenance==0.3.0'
```

## Publish while computation continues

Configure a cloud destination in your workspace. Existing native authoring and
execution calls durably queue their completed files and return after local
verification. A separate worker transfers and verifies those files. Publication
recovery retries the saved upload without rerunning training or evaluation.

Use one outer `viper.storage.workflow` when a driver makes several related
calls, such as training followed by inference, evaluation and diagnostics.
Nested calls share that lifetime and keep their inputs available between calls.
The [cloud storage guide](../how-to/cloud-storage.md) shows the configuration,
workflow scope, publication status and recovery operations.

## Choose local retention

`storage.offload` defaults to `false`. It controls local retention independently
of cloud publication. Set it to `true` to permit automatic deletion of managed
payloads after successful workflow completion, verified cloud publication and
completion of their readers.

Each artifact version can inherit the setting, keep a verified local copy, or
permit offload. One keep preference protects a payload shared by several
artifacts. A keep request restores an absent artifact before returning.

The resolver uses a verified resident original or shared store payload first.
It downloads only when the requested local bytes are absent. Downloads are
verified before becoming available. Inventory and location metadata remain
after deletion, so listing and retrieval keep using the original references.

## Compatibility and completion

Native cloud-configured runs can return successful scientific results while
publication is pending. Check `publication_status(..., wait=True)` after the
outer workflow closes when cloud durability is required before the source host
or disk is removed. Upload failures retain their local sources for recovery.
Hashing, durable local admission and cold restoration still require local work
or transfer time.

Existing explicit APIs that promise a verified cloud reference still wait for
verification. Explicit promotion remains available for older local runs. New
cloud-managed runs publish their original snapshots without converting them
into a second reference graph.

The serialized reference formats introduced in [0.2.0](0.2.0.md) remain the same.
A resolved filesystem path can change after restoration; saved references do
not. Code retaining a path must remain inside the workflow that protects it.
