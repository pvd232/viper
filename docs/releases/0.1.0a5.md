# VIPER 0.1.0a5

Version 0.1.0a5 adds reusable test-impact selection and durable, bounded cloud
artifact handling. Publication identity and registry evidence will be added
after the trusted release workflow completes.

## Shared file identity

`ResolvedFileRef`, `SnapshotFileRef`, and `ReuseFileIdentity` now inherit exact
byte count and SHA-256 fields from `FileIdentity`. The shared model removes
three copies of the same persisted identity while retaining their serialized
fields.

## Test selection for Python repositories

VIPER's test-impact engine now accepts declaration relationships independently
of repository layout and test runner. The existing pytest command and a new
unittest command translate repository-specific test names at the tool boundary.

`tools/build_test_impact_graph.py` runs the retained CodeQL analyzer against a
named Python repository. The resulting graph is bound to the analyzed source
bytes. When graph coverage ends before a known test, the test-runner adapter
returns the repository's declared fallback and widens the selection.

## Durable cloud artifacts

`ViperCloud` now owns VIPER's immutable cloud-storage boundary. Workspace
configuration selects either Google Cloud Storage or a Hugging Face repository;
the public execution APIs do not accept provider clients. Both providers return
self-describing immutable references and verify byte count and SHA-256 before
exposing bytes to a consumer. Large uploads and restores stream through files
instead of holding complete artifacts in memory.

Cloud-backed plans, stage snapshots, future inputs, and terminal run records
remain verifiable across machines. Preflight rejects an unreachable storage
graph before execution begins. A `resolved.ref.yaml` sidecar preserves each
terminal run's durable cloud identity, and `promote_run_to_cloud()` can migrate a
verified local run graph without rerunning its stages.

Cloud remains opt-in. Configuring a GCS bucket or Hugging Face repository preserves
the default local run destination; callers select cloud publication for a run or
explicitly promote one verified local graph.

After a successful run and an accepted result, callers may use
`retention.evict_cloud_backed_run_files()` to remove local output copies. The
operation verifies every local and cloud file before the first deletion,
preserves the run evidence and canonical inputs, and reports output and
temporary-workspace bytes separately.

## Bounded execution storage

Each stage now receives its own temporary runtime directory. VIPER removes
completed attempt materializations after their outputs have been retained,
which prevents repeated stages from accumulating redundant input copies.

Bundle artifacts, stage file-access receipts, and Python package metadata use
canonical ordering. Repeated verification also reuses an accepted upstream
run result within the current verification pass instead of reconstructing the
same dependency for every consuming stage.

## Large HTTP responses

HTTP retrieval verifies response bodies by hashing fixed-size chunks. The
digest and byte-count guarantees are unchanged, while verification no longer
copies the complete response into memory.
