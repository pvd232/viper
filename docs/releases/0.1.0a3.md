# VIPER 0.1.0a3 release report

VIPER 0.1.0a3 is a release candidate. Publication remains pending until the
local distribution, clean-installation, Mantra GPU, signed-tag, TestPyPI, and
PyPI gates pass.

## Release identity

The final report will record the release commit, signed tag, workflow run,
distribution filenames, byte counts, and SHA-256 digests.

## Scope

This release removes the experimental System Impact, graph-localization,
CodeQL, scheduling, contract-plan, fixture, and research-work surfaces. It
retains experiment execution, verification, storage, restoration, catalog,
knowledge, MCP, and the public CPU workflow.

## Acceptance status

The earlier candidate wheel passed its clean Python 3.14.5 installation, public API,
CLI, CPU quickstart, and generated-project gates. The repository also passed
its formatting, lint, type, unit, contract, integration, and host-independent
release gates. The report will add the supported-Python CI, Mantra GPU,
TestPyPI, and PyPI evidence as each boundary passes.

Those results describe the earlier build. Rebuild and validate distributions
from the final release commit before publishing; source changes produce a new
artifact identity.

The [earlier GPU receipt](receipts/v0.1.0a3-mantra-gpu.json) identifies the
previously tested wheel. Each subsequent build requires fresh acceptance.

Before publication, run `make check` and `make check-release`, build the wheel
and source distribution, and run `python -m twine check` on both files.
Verify clean installation and the live CUDA tests using the candidate wheel.
Require green CI for Python 3.11–3.14, then publish through the signed-tag
workflow. Include `CI-Run: <run-id>` in the signed tag message to select the
CI distributions used for GPU acceptance. Compare the published file hashes
with those validated distributions.

## Incompatible API changes

- Python run and benchmark results expose `status`, `path`, `record`, and
  `reference`. Replace `resolved_run_path` and `result_path` on these wrappers
  with `path`; replace `resolved_run` and `result` with `record`, and
  `resolved_run_ref` and `result_ref` with `reference`. The nested result in a
  batch uses the same names. Stored terminal records keep their existing fields.
- Import objects from their defining modules. Package-root
  re-exports of individual classes and functions have been removed.
- Use `viper.config` classes and the `config=` argument for stage and metric
  configuration. Replace parameter-model declarations with config classes.
- Declare stage outputs with `StageOutputs`, `TrainOutputs`, or `EvalOutputs`
  and `output()`. Stage functions write through `context.outputs`; completed
  files are recorded as artifacts.
- Training uses the names `model` and `resume_state`. Evaluation reads `model`
  and `test` and writes `predictions`.
- Stage documents use schema version 2. Regenerate earlier stage documents
  through the current authoring API.
- Use `serialize_document()`; the `serialize_record()` alias is removed.

The [Python API](../reference/api.md) and [configuration guide](../reference/configuration.md)
show the current imports and declarations.
